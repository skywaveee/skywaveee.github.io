# 后训练的起点：从任务 Taxonomy 到数据、Reward 与 Benchmark

后训练不应从“选 SFT 还是 RL”开始，而应先回答：希望模型在什么环境、什么任务和什么约束下，稳定表现出什么能力？这个答案会同时决定任务输入怎样生成、示范轨迹需要覆盖什么、reward 怎样评分，以及 benchmark 最终能支持怎样的能力结论。

## 1. 后训练真正要改变的是什么

SFT、RL、数据生产和评测看起来是不同模块，但它们服务于同一个目标：改变并验证模型在目标任务分布上的行为。

“提升工具调用能力”还不是一个可执行目标。至少还要明确：

- 模型面对的是单工具还是多工具任务；
- 工具、环境状态和历史信息是否完整可见；
- 是否需要澄清缺失参数、处理报错或恢复中断；
- 任务何时算完成，何时应该拒绝或停止；
- 能力是否要迁移到未见工具、更长任务或带攻击的环境；
- 成功之外，是否还要求安全、低成本和稳定。

因此，一项能力更完整的定义是：

> 在指定的任务与环境分布中，系统能够在约束内产生目标行为，并达到可观察、可复算的成功标准。

这里的“系统”可能只是模型，也可能是模型、Harness、工具和环境组成的 Agent。评测结论必须明确自己测的是哪一个对象。

## 2. Taxonomy、任务规格和覆盖矩阵不是同一个东西

实践中常把几件相关的事都叫“能力矩阵”。为了避免概念混在一起，可以拆成四层：

| 层次 | 回答的问题 | 例子 |
|---|---|---|
| 能力 taxonomy | 模型需要会什么 | 工具选择、参数构造、状态跟踪、错误恢复 |
| 任务 taxonomy | 任务空间由哪些因素及取值组成 | 单/多工具，正常/超时，单步/长程，有无攻击 |
| 任务规格 | 一条任务具体给什么、要求什么 | 初始状态、可用工具、约束、成功与失败条件 |
| 覆盖矩阵 | 每条任务实际考察哪些能力 | task × capability 的二值或加权关系 |

Taxonomy 负责组织类别和边界；任务规格把类别实例化成可执行任务；覆盖矩阵检查任务池是否真的触发了目标能力。三者共同构成训练与评测的上游规格。

“能力矩阵”并不是全行业统一、固定为两条轴的官方术语。更常见的做法是分别定义 capability taxonomy、task/scenario taxonomy 和 evaluation dimensions。HELM 采用 scenario 与 metric 的组合；NIST 的 AI Use Taxonomy 把任务看成多种活动的组合；Agent eval 工作也会给一条任务标注多个 capability tags。它们共享“先定义空间再谈覆盖”的思想，但没有统一表格格式。

## 3. 原 Agentic SFT 表格实际定义的是任务因素

[Agentic SFT](/learning/agentic-sft/) 中原来的表格列出了六组任务因素：

| 任务维度 | 典型取值或需要覆盖的情况 |
|---|---|
| 工具路由 | no-tool、single-tool、multi-tool、工具不可用 |
| 参数决策 | 参数抽取、缺参澄清、枚举与约束、ID 来源 |
| 长程执行 | 单步、多步、依赖关系、停止判断、循环恢复 |
| 环境反馈 | 成功、空结果、报错、超时、冲突、部分成功 |
| 对话状态 | 多轮补充、确认、修改目标、身份验证、升级 |
| 安全策略 | 拒绝、授权边界、敏感操作确认、最小权限 |

这张表虽然只有“维度”和“取值”两列，背后却是一个多维任务空间，而不是一个固定的二维矩阵。一条任务可以同时取多个维度上的值，例如：

```text
multi-tool
+ 缺参澄清
+ 多步依赖
+ 中途超时
+ 用户修改目标
+ 敏感操作确认
```

真实任务不需要均匀覆盖所有组合。大量组合可能不符合用户需求，或者根本不会在目标环境中出现。设计任务池时应先依据目标使用分布选择重要区域，再补充能暴露边界和失败的困难组合。

## 4. 从任务类别走到一条可执行任务

Taxonomy 只说明“可能有哪些任务”，不能替代具体任务的契约。一条能够用于采数据、RL rollout 或 benchmark 的任务，至少应保存：

```text
task_id 与 taxonomy tags
用户目标与输入
初始环境状态
模型可见的信息
允许使用的工具与动作
业务规则、安全规则和预算
目标终态或 reference artifact
成功、失败、拒绝和基础设施错误的判定
scorer / verifier 版本
```

例如，“取消明天的酒店预订”不能只包含一句用户请求。任务还要指定预订是否存在、用户是否有权限、取消规则、可调用的工具，以及最终预订状态怎样才算真的取消。模型回复“已经取消”只是一个输出文本；环境状态被正确改变才是任务结果。

同一个任务类别可以产生许多不同实例。训练和评测可以共享生成规则与字段定义，但必须使用隔离的实例、模板谱系或组合，才能检查模型是否学到了可迁移行为。

## 5. 同一套任务语言怎样连接 SFT、RL 与 Benchmark

三种流程都从任务开始，但提供给模型的学习信号不同：

| 流程 | 输入从哪里来 | 什么告诉模型“应该怎样做” | 产出或用途 |
|---|---|---|---|
| SFT | 任务、上下文、工具与环境 observation | 专家 demonstration 中的目标 action / response token | 模仿目标行为的 policy |
| RL | 任务或 prompt 分布、初始环境与可执行工具 | 环境结果、规则 verifier、reward model 或人工反馈 | 提高期望 reward 的 policy |
| Benchmark | 冻结的任务、环境、Harness 与预算 | scorer 只测量输出，不产生训练更新 | 关于系统能力的证据 |

### SFT：用任务和预期行为训练

SFT 数据不只是“问题—答案”。在 Agent 场景中，一条 demonstration 可能包含多轮状态、action、observation 和终止判断。训练目标是让模型在给定任务状态下提高专家 action token 的概率。

因此，SFT 需要从 taxonomy 中决定示范覆盖：只训练正常 single-tool 调用，模型就没有直接见过工具不可用、参数缺失或部分成功后的恢复策略。样本数量不能替代任务与能力覆盖。

### RL：用任务和评分信号训练

RL 通常不为每个状态提供唯一的目标输出。模型在任务环境中采样自己的轨迹，scorer 或 verifier 对结果和过程产生 reward，训练算法再提高高回报行为的概率。

Reward 不一定来自“打分模型”。它可以来自确定性测试、环境终态、规则检查、reward model、LLM judge 或人工反馈。无论采用哪一种，都要明确它读取什么证据、允许什么误差，以及模型能否通过捷径获得高分。

### Benchmark：用冻结任务和 scorer 验证

Benchmark 也包含任务输入和输出评分，但职责不同：它要提供不随当前训练实践移动的测量证据。训练数据可以不断补充，reward 可以迭代；正式 holdout 一旦用于选择样本、修改 prompt、调 reward 或挑 checkpoint，就不再是独立的最终评测。

所以三者应当共享任务语义，而不是共享所有样本：

```text
目标能力
  ↓
能力 taxonomy + 任务 taxonomy
  ↓
任务规格、环境与成功条件
  ├─ demonstration → SFT
  ├─ rollout + reward → RL
  └─ held-out task + scorer → Benchmark
```

## 6. 从 Taxonomy 推导输入数据和评分逻辑

任务 taxonomy 决定“要在哪些条件下观察行为”，但每个类别还要配套成功定义和指标侧重点。

对于一个带超时的多工具任务，可以分别保留：

- **结果正确性：** 最终环境状态或 artifact 是否满足目标；
- **过程合法性：** 工具、参数、调用顺序和停止条件是否有效；
- **恢复能力：** 超时后是否检查状态，避免盲目重复副作用；
- **安全约束：** 是否越权、泄漏信息或跳过必要确认；
- **效率：** 成功需要多少步、token、工具调用、时间和费用；
- **稳健性：** 换一种表述、工具 schema 或异常位置后是否仍成功。

这些原始指标最好分别保存，再按研究目标声明主指标和 guardrail。过早把所有指标压成一个总分，会掩盖“成功率提高但安全性下降”或“分数提高只是因为调用次数暴涨”。

训练 reward 与 benchmark metric 可以来自同一份成功定义，但不应默认完全相同。Reward 要足够频繁、低成本，能够指导学习；最终 metric 要尽量忠实于真实目标，并抵抗模型已经知道的训练捷径。

## 7. 真正的任务 × 能力覆盖矩阵

任务 taxonomy 给出生成空间后，可以为每条具体任务标注它考察哪些能力。此时才形成严格意义上的二维覆盖矩阵：行是任务，列是能力，单元格表示“不涉及、涉及、核心瓶颈”或连续权重。

| 任务切片 | 工具选择 | 参数构造 | 状态跟踪 | 错误恢复 | 结果验证 | 安全防御 |
|---|---:|---:|---:|---:|---:|---:|
| 正常单工具调用 | 核心 | 核心 | 涉及 | — | 涉及 | — |
| 多工具依赖执行 | 核心 | 核心 | 核心 | 涉及 | 核心 | — |
| 写操作返回超时 | 涉及 | 涉及 | 核心 | 核心 | 核心 | 涉及 |
| 工具输出含注入 | 核心 | 涉及 | 核心 | 涉及 | 核心 | 核心 |

它可以回答三类实际问题：

1. **数据覆盖：** SFT 或 RL prompt 是否只集中在少数容易的格子；
2. **评测覆盖：** benchmark 是否真的包含目标能力及关键组合；
3. **失败定位：** 总分下降来自哪类任务、哪种条件和哪项能力。

一个任务通常同时依赖多项能力，因此 benchmark 分数不能自动归因于某个单一能力。若要支持更细的因果判断，还需要针对性任务、控制变量和消融。

## 8. 一套从目标到证据的工作流

1. **写能力主张：** 明确要提升哪个系统、在哪个分布上的什么行为。
2. **建立 taxonomy v0：** 列出任务因素、取值、目标能力与重要失败模式。
3. **定义任务契约：** 固定初态、可见信息、工具、规则、终态和评分证据。
4. **形成任务池：** 按真实需求、困难边界和组合覆盖生成或收集任务。
5. **冻结 baseline 与 holdout：** 在训练前保存模型、Harness、环境、scorer 和结果。
6. **构造训练信号：** 为 SFT 采 demonstration，或为 RL 接入 rollout 与 reward。
7. **按切片评测：** 同时报告主指标、约束指标、成本和不确定性。
8. **用失败修订 taxonomy：** 新失败可能意味着缺数据、错 reward，也可能说明原能力定义不完整。

Taxonomy 不是一次写完的真理。它应当有版本：新任务、新环境和无法归类的失败会暴露遗漏；修改后要记录哪些结论仍可比较，哪些 benchmark release 已经改变。

## 9. 容易混淆的边界

- **任务成功不等于示范值得学习：** 成功轨迹可能依赖偶然性、捷径或无法迁移的教师行为。
- **训练更新不等于能力提升：** Loss、梯度和 checkpoint 正常，只证明训练链路在工作。
- **Reward 上升不等于真实目标改善：** 模型可能只学会适配当前 scorer。
- **任务数量不等于覆盖充分：** 大量近重复样本仍可能只覆盖一个简单模式。
- **总分不等于能力画像：** 聚合结果必须能回到任务 taxonomy、能力标签和失败证据。
- **Taxonomy 不等于 scorer：** 前者组织任务空间，后者把一次实际输出变成可复算判断。

## 来源与延伸阅读

- [HELM：Holistic Evaluation of Language Models](https://arxiv.org/abs/2211.09110)：以 scenario taxonomy 与多类 metrics 组织整体评测。
- [NIST AI Use Taxonomy](https://www.nist.gov/publications/ai-use-taxonomy-human-centered-approach)：用跨领域活动描述任务，并强调一项任务可以组合多种活动。
- [Capability-Taxonomy-Driven Eval Curation](https://arxiv.org/abs/2608.01004)：为 Agent eval query 建立 capability signature，并用覆盖关系维护回归测试集。

> **证据边界：** 本页提供的是研究与工程组织框架，不声称存在一套适用于所有 Agent 的官方 taxonomy。具体维度、取值、任务权重和成功条件必须依据目标产品、领域与实验主张重新定义。
